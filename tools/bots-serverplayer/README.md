# ElytrixBotsTrain — ServerPlayer test

Test target: Leaf 1.21.11 build 179, Java 21. `/bots` opens the create/remove menu. One server-side player per owner; the entity is hidden by default and shown only to the owner, and removed from the owner's TAB. It is not registered in the global online player list, but it exists in the world and may still be observed by server plugins, mobs or other effects. Each owner can independently enable following, attacking and looking via the settings menu; all are initially disabled and persist in config.yml. Following uses straightforward player movement and jumping, not full pathfinding; it can get stuck behind obstacles or fall off ledges. Attacks use the server attack logic, with an empty hand and one-second interval. Non-owner/environment damage and entity interaction are cancelled. WorldGuard, PvP restrictions and other plugins can still cancel an owner's hit. Health is restored every tick; lethal damage is capped to protect it, so unusual very high damage is not vanilla.

The fake connection consumes outgoing packets. Because normal player knockback is applied client-side, the fake listener replays the server-computed velocity at its next tick. This is a test approximation, not a full Minecraft client. The bot's persistent data has `elytrixbotstrain:training_bot` (byte 1) and `elytrixbotstrain:owner` (UUID string), allowing future integrations to identify it. Do not globally bypass an anti-cheat; check the particular anti-cheat's APIs and account for its timing.

Build from the patched/running Leaf server directory: `JAVA=/path/to/java ECJ=/path/to/ecj.jar ./tools/bots-serverplayer/build.sh /path/to/leaf-runtime` (expects `versions/1.21.11/leaf-1.21.11.jar` and `libraries/`). Do not bundle server classes. Only Mojang-mapped 1.21.11 runtime is supported. No VirtualEntityApi dependency.

Local integration: exact supplied Leaf 179, offline-mode, Java 21, test helper and two synthetic clients. Confirmed owner-only tracking, damage via client attack packet, normal health recovery, server-calculated knockback, and a critical hit through server attack code. No visual Minecraft-client test, multi-version ViaVersion test, or test with the production plugins/anti-cheat was performed. Entity damage/particles/sounds may still be visible/audible to bystanders; packet-level isolation and compatibility need separate testing.

All bots use the signed Mojang texture of `rooyzee` captured at build time. Changes to the account skin will not automatically update the embedded texture. The 16-character username limit leaves four base-36 characters after `ElytrixBots_`. A client needs access to Minecraft texture servers to render the skin.

AI test: with a synthetic 1.21.11 client and an isolated copy of Leaf 179, followed across flat ground (z=2.5 to z=6.5), turned toward its owner, and landed unarmed attacks. Menu navigation and persisted toggles also tested. Full pathfinding, visual skins, ViaVersion clients, production plugins, and anti-cheat compatibility have not been tested.

Version 2.2-test requires GreatCombat 1.9 enabled. The GreatCombat pre-start event is cancelled only for the bot and its owner; existing combat state is not cleared. On an isolated Leaf server with GreatCombat 1.9, direct calls to its combat manager in both directions did not tag the owner, and an already active tag persisted. This did not test a full fight with a second real player or the production plugin stack. GreatCombat's own dependencies must be available. If it does not enable, the bot plugin disables itself.

Settings now include Crits, Combo, Pro, Noob and Custom. Presets override the three switches; Custom restores their values. Crits jumps and attacks only while falling; Combo chases and attacks frequently; Pro combines movement and periodic crits; Noob attacks less often and sometimes intentionally misses. They are simple heuristics, not full PvP pathfinding, and empty-hand vanilla attack cooldown limits their speed. On a flat test platform, Crits produced 1.5 damage critical hits, Combo 1.0, Pro a mixture, and Noob occasional hits; real client movement, balance, and combo quality need in-game testing.

Version 2.3-test registers ordinary menu handlers separately from the GreatCombat integration and looks up the event using GreatCombat's class loader. If the expected 1.9 API is absent or incompatible, menus remain protected but bot creation is disabled with a message; no unsafe fallback removes combat tags. If GreatCombat is disabled later, active bots are removed. Tested menu navigation both with GreatCombat 1.9 and with an enabled test stub lacking the event, and repeated the 1.9 combat-manager tag checks. The cause of a particular server's missing class can only be determined from its GreatCombat jar and startup log.
